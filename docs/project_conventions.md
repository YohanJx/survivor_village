# 余烬村庄 · 项目代码与架构规范

版本：2.0 · 生效日期：2026-10-08

适用范围：本项目的 GDScript、场景、自定义资源、游戏规则、UI、存档和测试。项目定位为 **卡牌生存经营 + 自动塔防**，使用 **Godot 4.5 / GDScript**，以当前 `project.godot` 为引擎基线。

本规范是后续开发的默认约定。新增代码必须遵循；旧代码按实际改动逐步迁移。保存规范不代表历史代码已经全部合规，也不要求为了格式化而改写无关逻辑。用户明确的新指令优先于本规范；规范调整须同步更新根目录 `AGENTS.md`。

## 零、效力、红线与阅读入口

本规范约束人工和 AI 生成的全部新增代码。它是项目要求，不代表当前仓库已经合规。**“能运行”只是最低条件，不能替代类型、架构和行为审查。**

- **必须 / 禁止**：验收阻断项。违反时修正代码，不能通过删测试、禁用检查或改文档掩盖。
- **应 / 默认**：正常选择；偏离时在变更说明中给出实际理由、影响和验证。
- **可**：按当前需求选用；不是要求引入更多框架、继承层级或文件。
- 优先级：用户明确要求 → 本项目规范 → Godot 4.5 官方文档 → 一般经验。引擎 API 事实以对应版本文档和实际验证为准。
- 显式类型、复杂度审查阈值、原生资源作为配置入口是**项目选择**；不能声称 Godot 禁止 `:=`、JSON、字典或条件分支。
- 不允许以“原型”为由把半迁移代码标记为交付完成。中断时记录已完成、未完成和验证状态，后续从记录继续。

## 一、基本原则

1. **显式、可读、可验证**：类型和职责在声明中表达，命名体现含义，错误在边界处理。
2. **数据驱动**：卡牌、费用、建筑、产出、效果和联动配置以原生资源组织，不在 UI 或场景脚本中堆放静态业务数据。
3. **单一事实来源**：一份运行时状态、一处规则结算入口；UI、预览和战斗不各自维护一套资源或伤害规则。
4. **依赖有方向**：管理者协调下层对象，下层通过信号报告事件；纯规则类不依赖场景树。
5. **按职责扩展**：沿用已有模型和可实例化系统；出现明确的复用或生命周期需求后再增加抽象、Autoload 或事件总线。

## 三、命名规范

| 对象 | 命名方式 | 示例 |
| --- | --- | --- |
| 类、`class_name`、自定义资源类型 | `PascalCase` | `CardDefinition`、`VillageState`、`CombatActor` |
| 场景树节点 | `PascalCase` | `CardList`、`HealthBar`、`VillageMap` |
| 枚举类型 | `PascalCase`，单数 | `Phase`、`Kind`、`Status` |
| 常量、枚举成员 | `UPPER_SNAKE_CASE` | `MAX_STAMINA`、`Phase.DAY` |
| 脚本、场景、资源文件和目录 | `snake_case` | `card_definition.gd`、`main.tscn`、`card_library.tres` |
| 变量、参数、函数 | `snake_case` | `current_stamina`、`apply_card_effects()` |
| 信号 | `snake_case`，表达事件或请求 | `health_changed`、`card_play_requested` |
| 私有变量、私有方法 | 单下划线前缀 | `_current_target`、`_calculate_damage()` |
| 信号回调 | `_on_事件名`，歧义时加入来源 | `_on_card_play_requested()`、`_on_pause_button_pressed()` |
| 新增分组、输入动作、稳定字符串 ID | 英文 `snake_case` | `zombies`、`pause_battle`、`emergency_training` |

这里明确区分**枚举类型名**和**枚举成员名**：写 `enum Phase { DAY, NIGHT }`，类型不是全大写。这与原始示例和项目现有 `GameTypes.Phase` 保持一致，也符合 [Godot 4.5 命名约定](https://docs.godotengine.org/en/4.5/tutorials/scripting/gdscript/gdscript_styleguide.html#naming-conventions)。

新命名类的脚本文件通常对应类名的下划线形式。现有 `game_state.gd` / `VillageState`、`card_button.gd` / `VillageCardButton` 保留，不仅为统一名称而破坏引用。入口脚本或不需要全局类型的局部脚本可以省略 `class_name`；不要注册与内置类或 Autoload 同名的类型。

其他要求：

- 布尔值优先用 `is_`、`has_`、`can_` 或语义明确的形容词，如 `is_active`、`has_target`、`can_afford`。
- 数值命名说明用途和单位；时间统一为秒，容易混淆时写 `duration_seconds`。地图格坐标用 `Vector2i`，世界坐标用 `Vector2`，转换集中在 `WorldLayout`。
- 区分定义 ID、手牌实例 UID 和战斗实体 ID；同一种卡牌可以有多个实例，不能以定义 ID 代替实例 UID。
- 中文用于玩家可见文本和解释性注释；代码标识符使用英文。避免 `data`、`temp`、`manager` 这类无法表达具体职责的名称。
- 下划线表示内部接口约定，不是 GDScript 的强制访问权限。其他模块不能因为成员仍可访问就绕过公共接口。

## 四、格式与可读性

- 文件使用 UTF-8、LF 换行、末尾换行；GDScript 使用 **Tab 缩进**，编辑器显示宽度建议为 4。
- 运算符两侧、逗号后留一个空格，不用额外空格对齐赋值。默认用双引号，浮点值写全 `0.0`、`150.0`。
- 顶层函数之间保留两个空行；声明区域之间保留一个空行。枚举成员逐行排列，方便注释和版本差异阅读。
- 行长以 100 字符为目标，通常不超过 120；资源路径或不可拆分文本可例外。长参数、长条件和容器内容分行。
- 多行表达式用括号，不用反斜线续行。使用 `and`、`or`、`not`；简单条件不额外套括号。
- 一个函数完成一个清晰任务；优先提前返回，减少嵌套。复杂 `match` 分支分行，不把完整控制流挤在一行。
- `##` 描述类职责、公共 API、规则前提和单位；`#` 解释原因、边界及不直观的实现。避免逐句复述代码或保留大段注释掉的旧代码。
- 不使用无说明的魔法数。业务平衡数值放配置资源；固定步长、结构上限等实现约束可使用有类型的命名常量。

## 五、脚本组织顺序

所有 `.gd` 按下面顺序排列，未使用的区域直接省略，不补空的 `pass` 方法或占位注释：

1. 文件级注解（需要时的 `@tool`、`@icon` 等）、`class_name`、`extends` 和类文档。
2. 信号。
3. 枚举。
4. 常量；如确需静态变量，紧随常量，公共在前、私有在后。
5. `@export` / `@export_storage` 变量；`@export_category`、`@export_group` 等紧贴其变量。
6. 公共运行时变量及属性。
7. 私有运行时变量及属性。
8. `@onready` 节点引用，公共在前、私有在后；默认作为私有依赖。
9. 引擎生命周期和虚方法：构造与初始化在前，随后处理、输入、绘制等回调，退出与清理在后。
10. 公共方法，包括公共静态方法和需要公开的规则接口。
11. 私有方法，包括 `_on_*` 信号回调和私有静态方法。

常见生命周期顺序为 `_init()` → `_enter_tree()` → `_ready()` → `_process()` → `_physics_process()` → 输入回调 → `_draw()` → `_exit_tree()`。这只是文件排列约定，**不是引擎每帧实际调用顺序**。如使用 `_static_init()`，放在构造回调之前。属性的 getter / setter 留在属性声明处；内部类确有必要时放在文件末尾。

声明初始化仅使用已经可用的依赖。普通成员初始化和 `_init()` 不访问尚未就绪的子节点；`@onready` 引用在 `_ready()` 前初始化，不能在 `_init()` 中使用。

## 六、严格显式类型

引擎允许动态类型和 `:=` 静态推断，但**本项目选择更严格的显式写法**：成员、局部变量、常量、循环变量、信号参数、函数参数及返回值都声明类型。匿名函数同样适用；没有返回值写 `-> void`。信号本身不声明返回类型。

```gdscript
signal stat_changed(stat: GameTypes.Stat, new_value: float)

const DEFAULT_SPEED: float = 150.0

var current_stamina: int = 100
var cards: Array[CardDefinition] = []
var cards_by_id: Dictionary[String, CardDefinition] = {}
var wall_damage: Dictionary[Vector2i, float] = {}


func calculate_damage(base_damage: float, armor_value: float) -> float:
	return maxf(0.0, base_damage - armor_value)


func collect_card_ids(definitions: Array[CardDefinition]) -> PackedStringArray:
	var card_ids: PackedStringArray = []
	for definition: CardDefinition in definitions:
		card_ids.append(definition.id)
	return card_ids
```

执行要求：

- 不写 `var speed = 150`，也不写 `var speed := 150.0`。写 `var speed: float = 150.0`。常量同样写明类型。
- 业务集合使用 `Array[T]`、`Dictionary[K, V]` 或合适的 `Packed*Array`。资源库存和建筑等级可以沿用由 `GameTypes` 枚举索引的紧凑数组，初始化与读档时校验长度。
- 核心数据优先使用 `CardDefinition`、`VillageStats`、`BattleReport` 等对象，不以字符串键的无类型字典模拟结构体，不以字符串比较阶段、效果或建筑类型。
- 对象型引用允许 `null`，使用前检查；可能已经释放的 `Node` 引用需要 `is_instance_valid()`。基本类型不以 `null` 表示缺失。
- 动态节点或资源加载时写明预期类型，必要时用 `as`，然后处理转换失败。`as` 不等于成功校验。
- 优先使用 `maxi()` / `maxf()`、`clampi()` / `clampf()` 等与数值类型对应的函数。浮点结果比较使用合适容差，不要求完全相等。
- 引擎虚方法遵循原始签名。引擎返回异构数据、JSON 导入或其他不可避免的动态接口允许显式 `Variant` / 无类型容器，但只存在于边界适配函数；注明原因并校验、转换后进入强类型核心。
- 内联属性 `get:` / `set(value):` 不支持独立标注参数与返回类型，由属性声明确定；拆成普通函数的访问器必须写类型。语法限制见 [GDScript 属性文档](https://docs.godotengine.org/en/4.5/tutorials/scripting/gdscript/gdscript_basics.html#properties-setters-and-getters)。
- Godot 4.5 不支持任意嵌套的类型化容器。需要复杂层级时定义资源或记录类，不写 `Array[Array[int]]` 这类无效签名。类型化集合的部分方法仍返回动态值，需要显式接收并检查。

类型能力及限制参照 [Godot 4.5 静态类型文档](https://docs.godotengine.org/en/4.5/tutorials/scripting/gdscript/static_typing.html)。不要仅通过关闭类型警告、使用 `Variant` 或随意添加 `@warning_ignore` 来绕过错误；确需忽略时精确说明原因。

## 七、数据、定义与运行时状态

### 7.1 资源配置

- 卡牌属性、费用、前置、建筑产出、修正器和联动配置使用继承自 `Resource` 的类型，实例保存为 `.tres`。
- 沿用 `CardDefinition`、`ResourceCost`、`BuildingRequirement`、`CardEffect`、`StatModifier`、`BuildingDefinition`、`ProductionProfile` 和 `CardLibrary`，不另建 `CardData` / `BuildingCardData` 同义体系。
- 配置字段使用 `@export`；长文本使用 `@export_multiline`；有范围的数值使用 `@export_range`。分组按基本信息、费用、前置、效果等职责组织。
- 数据类可包含局部查询、校验或规则方法；不能寻找场景节点、更新 UI、播放声音或持有当前游戏的全局引用。
- 自定义资源如提供 `_init()`，所有参数都必须有默认值，保证编辑器、资源加载和复制可以无参创建。

### 7.2 共享定义与独立实例

- `CardDefinition`、`BuildingDefinition` 和资源库属于共享定义，游戏运行中按只读处理。
- `CardInstance` 保存手牌实例身份；临时修正器保存持续时间和来源；战斗记录保存当前生命、位置、路径和冷却。不要把这些状态写回共享定义。
- `VillageStats`、`BattleReport` 和 `VillageSaveData` 虽然继承 `Resource`，但属于每局或每次结算独立持有的运行时数据；它们不等同于只读配置。
- 需要修改资源实例时明确创建或复制；对包含资源的数组、字典和深层引用逐项核查。`duplicate(true)` 不能替代对实际共享关系的检查。
- 存档和黄昏快照需要隔离可变数组、字典和嵌套状态；后续结算不能反向改写之前的快照。

这些要求来自本项目对数据生命周期的划分；资源缓存和自定义资源构造细节可查 [Godot 4.5 资源文档](https://docs.godotengine.org/en/4.5/tutorials/scripting/resources.html)。

## 八、系统职责与依赖方向

| 现有类型 / 脚本 | 应承担的职责 | 边界 |
| --- | --- | --- |
| `GameTypes` | 统一枚举、名称、索引和共享结构常量 | 不保存当局进度 |
| `CardCatalog` | 加载原生资源库、按 ID 查询、组织显示信息 | 不执行卡牌效果 |
| `VillageState` / `game_state.gd` | 阶段、资源、建筑、手牌、事务、结算、奖励和存档 | 不绘制 UI、不负责逐帧战斗 |
| `EffectResolver` | 统一效果执行和派生属性计算 | 预览计算不修改原始状态；不依赖节点树 |
| `BuildingSynergy` 及子类 | 明确且可配置的设施联动与优先级 | 不按 UI 操作顺序决定规则 |
| `BattleSimulation` | 固定步长模拟、生成、索敌、寻路、伤害和战报 | 不直接操作 UI；完成时发信号 |
| `WorldLayout` | 网格、坐标转换、地形和建筑占地 | 不维护第二份资源或阶段状态 |
| `VillageMap` | 读取状态和战斗记录并展示地图 | 不扣资源或推进阶段 |
| `main.gd` | 组装依赖、连接信号、输入协调与界面刷新 | 不复制业务公式 |
| `VillageCardButton` | 单卡展示、焦点和点击事件 | 不决定费用结算和卡牌是否真正生效 |

### 8.1 通信

- **向下调用**：父节点、管理者或上层系统可以通过公开方法控制其拥有的组件。
- **向上发信号**：卡牌点击、单位死亡、战斗结束等事件由产生者发信号，上层连接并处理。事件参数携带稳定 UID 或必要的类型化结果。
- **同级由管理者协调**：UI 不直接持有并修改另一组件的内部状态；共同管理者连接信号或注入接口。
- 禁止 `get_parent().get_parent()`、`/root/Main/...` 等跨层级路径获取业务管理者。允许组件引用自己拥有的固定子节点。
- 默认连接具体对象的信号。只有确实跨场景且无共同所有者的事件才考虑全局事件总线，且仍保留明确的类型与职责。
- UI 的卡牌请求应携带 `uid: int`，由管理者调用 `VillageState.play_card(uid)`；成功后状态发出变更信号，界面按状态刷新。
- 避免同一状态变更在状态层、UI 层和动画回调重复执行。信号在完整状态提交后发出，避免观察者读取半成品。

### 8.2 Autoload 的使用范围

跨场景的设置、音频、场景流转等全局生命周期服务可以使用 Autoload。每个服务明确职责，在 `project.godot` 中注册，名字不与 `class_name` 冲突。

当前项目未注册 Autoload；`VillageState` 和 `BattleSimulation` 是可独立实例化的 `RefCounted`，由入口持有。继续保留这种按局拥有的边界；`EffectResolver` 等纯计算类也不因“系统级逻辑”这一称谓自动改成单例。未来新增全局服务时说明为什么需要跨场景生命周期。机制参照 [Godot 4.5 Autoload 文档](https://docs.godotengine.org/en/4.5/tutorials/scripting/singletons_autoload.html)。

## 九、场景与对象生命周期

- 固定场景中的局部子节点可通过有类型的 `@onready` 引用；可使用场景唯一名称 `%HealthBar`，前提是场景确已配置唯一名称。
- 代码动态创建的 UI 使用创建时的类型化引用；可复用组件通过公开 `configure()` 或 `setup()` 接收依赖。不要对动态节点假设固定场景路径。
- `_ready()` 负责连接和初始化；需要反复配置的对象防止重复连接。长生命周期信号源与短生命周期订阅者之间，明确连接、解绑和对象有效性。
- 场景对象通常用 `queue_free()` 销毁；延迟回调、异步返回、Timer 和跨帧目标引用在访问前检查有效性。
- 场景实体检索统一使用已约定的分组，例如 `&"zombies"`；检索结果先按明确类型过滤，再调用公开接口，不依赖节点树层级。
- **当前战斗模型不属于场景实体**：`CombatActor` 是记录对象，索敌使用 `BattleSimulation` 的类型化集合。分组规则适用于未来真正的 `Node` 实体，不能对 `RefCounted` 调用节点分组 API。
- 不在每帧反复执行整个场景树搜索、加载资源或重建静态界面；缓存稳定依赖。是否增加空间索引或对象池应由规模和实际性能测量决定。

## 十、昼夜循环与规则不变量

以下是所有新功能和规则迁移必须维护的目标，不是对现有实现已经全部验证的声明。

### 10.1 状态与卡牌事务

- 阶段统一使用 `GameTypes.Phase`：`DAY` → `NIGHT` → `REWARD` → 次日 `DAY`，失败进入 `GAME_OVER`。UI 不能用字符串维护平行状态机。
- 白天清晨、午后、黄昏三个时段，每时段行动额度在黎明由 `WorkforceRules` 按人口确定，当天不因招募追加额度。成功执行或待命消耗一次行动，额度用完才推进时段。卡牌被拒绝时，不消耗资源、不移除实例、不执行部分效果、不推进时间。
- 职业人数合计必须等于人口，职业枚举和原生规则资源是统一配置。缺少对应职业禁止解锁与执行卡牌，不能以更高体力代替准入。重复体力费用先汇总，再应用职业倍率并统一向上取整；其他资源费用不打折。名册、额度和已用行动必须保存、校验并隔离复制。
- 先校验阶段、实例存在、全部前置、等级上限及合计费用，再整体提交。重复费用项按资源汇总；涉及扣除的效果同样纳入可支付校验。
- 校验和预览使用同一规则来源。不能在 UI 内凭颜色或余额自行认定合法，也不能用静默钳制负余额掩盖事务错误。
- 可重复卡保留实例；一次性卡按实例 UID 消耗。奖励卡先加入手牌，只有玩家后续执行时才产生卡牌效果。
- `begin_night()`、战斗结束、奖励确认和黎明结算需要校验来源阶段，重复调用不能重复扣费、奖励或推进日期。

- 地形按种子与原生地图参数生成网格；勘探必须显式选择与已探索区正交相邻的未知目标，距离体力进入统一费用入口。线索不等于发现，预览/未知区渲染不揭示目标资源。探索路线、目标与完成记录进入版本化存档，恢复前验证连续性与真实发现集合。
- 所有发展卡共用营地、勘探、职业、地形、设施及制作前置；卡牌完成依赖使用原生定义的稳定 ID，拒绝未知引用与循环。UI 只发选格请求，状态持有地形和路线；生成、费用与前置不得在展示层复制计算。
- 卡牌关键词引用原生 `KeywordDefinition`，使用稳定 ID 与主题/地形/人物分类；地形与人物条件须同时满足，主题仅分类解释。显示、奖励与执行共用准入，禁止从文本匹配推导规则。
- 第一天只开放地形勘探；解锁共用发现、工具、设施与职业前置。打井先发现地下水候选地，再备工具并由采集者与工程师勘探井位，实际提交才抽取成功机会；预览只展示成功时结果。见 [生存逻辑顺序](survival_progression.md)。

### 10.2 效果与设施联动

- 派生属性统一按 **基础值与加法 → 所有乘法 → 安全下限 / 上限** 处理，不依赖修正器加入顺序。
- 新效果进入 `CardEffect` 和 `EffectResolver` 的统一执行流程，不在 UI、战斗或某张卡的展示脚本中额外扣费或修改相同属性。
- 设施独有联动优先实现为 `BuildingSynergy` 子类，通过 `BuildingDefinition.synergy` 配置，由 `EffectResolver.derive()` 统一调用。
- 供电优先级必须确定且可解释。相同优先级的规则需要明确稳定次序或额外排序键，不把偶然的容器遍历顺序当作规则。
- 临时效果的作用范围、叠加规则、持续夜数和过期时点明确建模；配置上的持续时间不直接作为共享资源的倒计时。

### 10.3 黄昏与黎明

- 天气定义与四时段色板使用原生 Resource。当日天气由 `VillageState` 持有、黎明更新并写入存档，独立种子/日期序列不消耗奖励或战斗 RNG；读档不得重新抽取。天气效果由 `EffectResolver` 派生，进入黄昏快照并在黎明一次结算；`MapAtmosphere` 只绘制光照、雨雾与闪电，不参与规则。

- 黄昏计算并保存 `night_stats`，冻结当晚的派生属性和供电分配；电力只预扣一次。
- 恢复夜间存档时沿用黄昏快照，不能重新扣电；当前设计从该夜黄昏重新模拟，而非恢复任意战斗帧。
- 黎明统一读取当晚快照结算生产、设施消耗和恢复；人口口粮按存活人数调整，不能按多个 UI 刷新重复结算。
- 当日产出与消耗后，食物、水、电力仅保留各自存储设施容量内的余量，无设施清零；容量与生产能力分开。
- 围墙损伤、人口伤亡和村庄耐久在战报中明确传回；持久结果进入状态，临时效果在约定结算点过期。
- 资源范围、等级上限、最低攻击 / 生命等约束集中维护；规则失败返回清晰原因，不能只在界面上隐藏按钮。

## 十一、自动战斗与随机数

- 当前逻辑步长为 **`1.0 / 30.0` 秒**。后续触及该实现时提取为有类型的命名常量；渲染帧使用累加器驱动多个固定步。
- 暂停和 1 / 2 / 4 倍速改变模拟推进速度，不能改变每个逻辑步的长度。动画和绘制不得参与伤害判定。
- 规则使用明确持有的 `RandomNumberGenerator`，以运行种子和需要的随机状态驱动；奖励与战斗采用明确的随机序列边界。
- 不在规则中调用无约束的全局随机函数、实时时钟或依赖节点树偶然顺序。实时时钟只可在创建新局时生成初始种子。
- 同一种子、输入和初始状态在同一引擎基线下应得到可复现结果；不承诺不同 Godot 版本或平台的浮点、物理结果逐位一致。
- 战斗修改集中在模拟器；表现层读取记录。移除集合元素时使用安全的倒序遍历或延迟移除，不能漏处理相邻死亡单位。
- 建筑占地和围墙改变时同步导航数据；索敌和路径失效都有处理策略。战斗超时或无可达目标需要明确结束行为，避免无限循环。
- 远程攻击、单位生命、冷却、弹体和围墙数据使用现有类型化记录，不重新引入异构字典。

## 十二、UI 与输入

- 组件显示 `CardDefinition`、`CardInstance`、`VillageStats` 或明确的展示模型；不继续扩散旧的 `Dictionary` 卡牌结构。
- 展示依赖的业务值来自状态、目录或统一规则查询。收益、风险、费用、锁定原因和联动预览不能各写一套公式。
- 点击、键盘输入和奖励选择通过上层协调进入公共状态接口；按钮禁用只是体验控制，业务接口仍必须自行校验。
- 可复用输入使用项目注册的 Input Map 动作，动作名采用 `snake_case`；UI 消费输入后避免同一事件再触发游戏操作。
- 刷新频率按信息变化需求选择。状态变化驱动主要界面更新，夜战数值可限频刷新；不每帧重建完整卡牌树。
- 玩家可见文本直接说明行为和失败原因，不展示类型、资源路径等实现细节。新增可翻译内容进入统一翻译流程时，不用显示文本充当稳定 ID。
- 卡牌费用与确认按钮放在滚动区之外；村庄信息使用独立场景窗口，不与卡牌详情共用标签页。词条通过 `KeywordDefinition` / `KeywordLibrary` 配置及 `RichTextLabel` hint 展示，高亮解释不得复制业务结算。

## 十三、存档、错误与兼容性

- 正式存档路径为 `user://village_save.tres`，当前模型为 `VillageSaveData`；配置保存在 `res://data/`，二者用途分开。
- 快照包含版本、种子与 RNG 状态、阶段、日期 / 时段、库存、建筑、实例 UID、临时效果、奖励、损伤以及结算所需快照。
- 先完整校验资源类型、格式版本、枚举范围、数组长度、资源范围、引用存在、UID 唯一性和阶段所需数据，再写入当前状态。
- 加载失败返回失败结果并说明原因，不能部分恢复。重新读盘时考虑资源缓存，不能把缓存中的旧内容当作刚写入的存档。
- 保存采用同目录临时文件，检查写入成功后再替换正式文件，检查替换错误。失败保留旧存档；仅创建新村庄界面不应自动覆盖待继续的旧进度。
- 资源定义 ID 和枚举索引是兼容接口。给存档或数组使用的枚举增加成员时保持旧数值；新存储枚举优先明确数值。改名、重排、删资源或改路径时制定映射 / 迁移，或明确拒绝不兼容版本并保留原文件。
- 恢复配置引用时按稳定 ID 查回当前资源库，避免把过期定义当作当前配置。不能把场景节点、UI、信号连接或模拟器实例当存档内容。
- 测试使用独立路径并关闭玩家自动存档；任何测试都不能覆盖用户的 `user://village_save.tres`。
- 可预期的失败通过清晰返回值或结果对象处理；开发错误使用断言或错误日志。不能让发布版业务校验只依赖 `assert()`，也不能吞掉 `ResourceSaver` / 文件操作错误。

## 十四、新功能的标准扩展流程

### 添加卡牌

1. 在 `data/cards/` 新建 `CardDefinition` `.tres`，填写稳定 ID、类型、名称、描述、收益、代价、标签及是否复用。
2. 组合已有的 `ResourceCost`、`BuildingRequirement` 和 `CardEffect`。同一事务中的费用与负效果可整体支付。
3. 在 `data/card_library.tres` 的 `cards` 注册；按前置必定发放的基础行动加入 `starting_cards`；第一天仅发放勘探，后续按统一前置开放。
4. 添加新效果种类时，同步完善类型、执行、校验、预览和存档兼容；不为组合已有效果的每张卡写独立脚本。
5. 验证资源加载、缺少前置、资源不足、重复使用 / 消耗、奖励获得与实际执行的差别。

### 添加建筑或联动

1. 在 `data/buildings/` 新建 `BuildingDefinition` `.tres`，配置 ID、等级上限、占地、修正器和产出。
2. 在资源库注册，并维护 `GameTypes.Building` 的稳定索引、名称及相应容量。
3. 定义占地和导航影响。现有占地由 `BuildingDefinition.footprint` 提供，通过 `WorldLayout` 消费；特殊布局才修改布局逻辑。
4. 独有联动在 `scripts/resources/synergies/` 新建子类并挂到建筑定义，明确供电优先级、触发前提和停用原因。
5. 验证单独使用、与其他设施组合、缺电 / 缺补给、升级、快照和夜间恢复。

### 添加 UI 组件

1. 组件只拥有自身显示数据和节点，公开类型化配置接口及请求 / 事件信号。
2. 在入口或共同父节点注入数据并连接信号，业务操作进入状态公共方法。
3. 检查鼠标、键盘焦点、禁用状态、重复输入、窗口缩放和目标消失后的显示。

## 十五、规范化脚本模板

模板用于展示组织和类型规则，不要求每个类包含所有区域。下面两个完整脚本可独立检查语法；实际新增业务类型时沿用项目已有类名和数据模型。

### 15.1 节点脚本模板

```gdscript
class_name ExampleSurvivor
extends CharacterBody2D
## 展示节点脚本的声明顺序、显式类型和向上通知。

signal health_changed(current_health: int)
signal died

enum Status {
	IDLE,
	WORKING,
	RESTING,
}

const DEFAULT_SPEED: float = 150.0

@export_range(1, 999) var max_health: int = 100
@export var movement_speed: float = DEFAULT_SPEED

var status: Status = Status.IDLE
var movement_direction: Vector2 = Vector2.ZERO

var _health: int = 0

@onready var _visual: CanvasItem = get_node_or_null("Visual") as CanvasItem


func _ready() -> void:
	_health = maxi(1, max_health)
	_update_visual()


func _physics_process(_delta: float) -> void:
	velocity = Vector2.ZERO
	if _health > 0 and status == Status.WORKING:
		velocity = movement_direction.normalized() * movement_speed
	move_and_slide()


## 伤害结算完成后通知管理者；死亡事件只发送一次。
func take_damage(amount: int) -> void:
	if amount <= 0 or _health <= 0:
		return
	_health = maxi(0, _health - amount)
	_update_visual()
	health_changed.emit(_health)
	if _health == 0:
		died.emit()


func _update_visual() -> void:
	if is_instance_valid(_visual):
		_visual.modulate = Color.WHITE if _health > 0 else Color.GRAY
```

这里移动速度单位为每秒像素，`move_and_slide()` 使用 `velocity`，不再手动乘 `delta`。`Visual` 是示例中的可选局部子节点；业务管理者应连接 `died`，由管理者决定后续处置。当前项目仍使用 `CombatActor` 模拟模型，不因这个模板改造现有战斗。

### 15.2 Resource 脚本模板

```gdscript
class_name ExampleBuildingCardData
extends Resource
## 展示资源字段分组和无副作用查询；仅用于规范示例。

@export_category("Basic Info")
@export var card_id: String = ""
@export var card_name: String = "未命名建筑"
@export_multiline var description: String = ""

@export_category("Resource Costs")
@export_range(0, 999) var food_cost: int = 0
@export_range(0, 999) var water_cost: int = 0
@export_range(0, 999) var electricity_cost: int = 0


## 检查费用，不扣资源、不修改定义、不操作场景节点。
func can_afford(
	available_food: int,
	available_water: int,
	available_electricity: int,
) -> bool:
	return (
		available_food >= food_cost
		and available_water >= water_cost
		and available_electricity >= electricity_cost
	)
```

此模板保留直观的费用示例。**实际项目使用 `CardDefinition.costs: Array[ResourceCost]` 与 `VillageState.can_play()`**，不要复制示例类再建立第二套费用字段或完整卡牌合法性判断。

必须检查错误日志和测试结果，不能仅凭进程退出码认定脚本全部通过。`tests/run_tests.gd` 验证原生资源规则；`tests/run_ui_tests.gd` 实例化真实主场景并隔离手动存档，图形模式保存截图。当前执行记录见 [整改验收记录](validation_report.md)，后续改动不能直接沿用旧成绩。已知问题和验收状态统一记录在 [技术债清单](technical_debt.md)，不在规范中长期保存易过期的“已通过”声明。

在文件写入受限的环境中，默认日志目录不可写时，追加 `--log-file /tmp/emberhaven_validation.log` 指定可写日志；不要为日志问题修改玩家存档路径或禁用错误输出。

### 16.3 完成前检查

- 命名、声明顺序、显式类型和格式符合本规范；无引入的新解析或类型错误。
- 配置与运行时状态分开，依赖方向明确；新增资源、枚举和引用都完整注册。
- 操作失败不产生部分效果，阶段推进和结算不会重复；共享定义和快照不会被意外修改。
- 按实际范围完成验证，说明命令、结果及未解决的限制；不得把“未运行”写成“已通过”。
- 功能或格式变化同步 README，规则变化同步相关测试，规范变化同步 `AGENTS.md`。
- README 面向玩家，介绍游戏、玩法、操作与下载安装；开发规范、架构、测试、存档格式和验收细节放在 `docs/`，README 只保留简短开发文档入口。开发入口见 [开发指南](development_guide.md)。
- 保留无关文件和用户已有改动，不为遵守规范批量重写项目。


## 十七、模块规模与接口设计

### 17.1 责任先于文件数量

新增功能先回答四个问题：**谁拥有状态、谁允许修改、谁负责计算、谁负责展示？** 没有明确答案时不能继续堆进 `main.gd`。

- 普通脚本超过 **300 行**、一个函数超过 **50 行**、条件嵌套超过 **3 层**，必须检查是否混入多个职责。行数包含空行，是触发审查的信号，不是自动判定错误。
- 超限代码优先按真实组件、独立规则、边界适配拆分；确实连续且单一的算法或绘图过程可保留，须写明理由与验证。禁止为满足数字把一段流程机械切成许多只有一次调用、名称含糊的小函数。
- 新增公共函数超过 **4 个业务参数**时审查是否缺少明确上下文对象；Godot 虚方法签名不受该阈值约束。不能用无类型字典“参数包”逃避。
- `main.gd` 应协调状态、模拟器和展示组件；新增卡牌面板、村庄面板、奖励弹窗等独立 UI 时使用自己的场景/脚本。
- 静态 UI 层级、主题和常规布局默认用 `.tscn` / `Theme` 资源编辑。动态生成仅用于数量随数据变化的实例，不在入口脚本中继续铺设数百行固定布局。
- 不新增“万能工具类”、服务定位器、反射式效果执行器、空的基类体系或仅有一个实现却没有扩展需求的工厂。

这些规模值是本项目的审查策略。Godot 的场景组织建议强调独立职责和由上层注入外部依赖；本项目将它落实为以上边界。[官方场景组织](https://docs.godotengine.org/en/4.5/tutorials/best_practices/scene_organization.html)

### 17.2 公共接口的契约

每个会改变状态的公共操作必须说明：允许的来源状态、输入范围、成功后的变化、失败是否修改状态、触发哪些信号。查询函数不能偷偷存档、抽随机数、推进时段或写回定义。

- `VillageState` 是当局资源、人口、建筑、手牌和阶段的写入所有者；`EffectResolver` 是它调用的受控规则执行者。
- `BattleSimulation` 拥有战斗记录，结束后提交 `BattleReport`；表现层读取记录但不修改生命、目标、路径或冷却。
- 返回容器时说明是只读借用还是独立快照。下划线和类型声明都不会自动保证深层只读。
- 方法名不能和实际副作用相悖：`get_` / `find_` / `preview_` 不执行游戏操作；保存、加载、结算使用明确动词。
- 修改接口必须同步所有调用方、测试、资源脚本引用和文档示例。禁止永久保留两个语义相同、行为不同的入口。
- 可预期失败使用明确结果；简单操作可以 `bool + last_error`，错误种类被多个调用方处理时引入类型化结果。禁止调用方解析中文错误消息决定玩法。

## 十八、枚举、字符串、字典与分支的正确边界

### 18.1 表达方式选择

| 情况 | 使用 | 不使用 |
| --- | --- | --- |
| 阶段、资源种类、敌人类别等有限集合 | 枚举、类型化属性 | 拼写敏感的字符串比较 |
| 同一模型的一组必需字段 | Resource 或 RefCounted 类 | `Dictionary[String, Variant]` |
| 同类对象的有序集合 | `Array[T]` | 无类型 Array |
| 坐标到围墙、稳定 ID 到定义的索引 | `Dictionary[Vector2i, WallSegment]` 等 | 为禁止字典而写逐个 if 或手动线性搜索 |
| 紧凑数值库存/派生值 | 经长度校验的 Packed 数组 + 枚举 | 裸数字下标散布在业务代码中 |
| 输入动作、信号名、分组 | `StringName` / `&"pause_battle"` | 每帧拼接重复名称 |
| 玩家文案 | String、后续本地化键 | 把显示名称当逻辑 ID |
| 外部导入/交换数据 | 边界解析、校验并转换 | 外部动态结构直接流入核心模型 |

现有卡牌 `id: String` 是稳定内容标识，允许在目录和存档边界查询；不为外观一致而改动既有 ID 类型或全部重排枚举。Resource 引用已经可用时直接使用引用。

### 18.2 条件分支与多态

- `if` 用于条件成立与否、边界检查、早返回；小范围 `match` 可分派封闭枚举。它们本身不是坏代码，也不能仅按数量认定性能瓶颈。
- 多个调用方重复根据同一类型分派相同业务，或添加一种设施需要修改多处大分支时，应把差异封装到现有规则对象/子类。
- 当前通用效果可以由 `CardEffect.Type` 在统一执行器分派；设施特有行为由 `BuildingSynergy.apply()` 多态实现。不要为了消灭一个小 `match` 给每个整数操作增加一个类。
- 新卡牌组合现有效果时只改资源；新增效果语义才扩展规则接口。
- 不使用 `get("attack")`、`set("health", ...)` 或拼接方法名替代已知类型的直接字段/方法。必要的编辑器反射或导入接口必须隔离在边界。
- 不把所有字典换成数组作为“性能修复”。索引结构按访问方式选择，优化效果用测量确认。Godot 文档也分别讨论了数组与字典的适用访问方式。[官方数据选择](https://docs.godotengine.org/en/4.5/tutorials/best_practices/data_preferences.html)

## 十九、配置完整性、效果执行和数值规则

### 19.1 配置是需要验证的输入

`@export_range` 和 Inspector 下拉框改善编辑体验，不能替代加载时校验。

资源库初始化或专门的资源校验入口至少检查：

1. 卡牌稳定 ID 非空、唯一；建筑枚举合法、唯一且所有必需索引完整。
2. 数组无意外空元素；所有费用、前置、效果和嵌套资源具有正确类型。
3. 金额非负、费用合法、持续时间有效；所有浮点数有限，不接受 NaN / Infinity。
4. 构造效果必须引用建筑；修正效果必须引用修正器；未使用字段不会产生隐式行为。
5. 前置指向已注册建筑，等级没有超出其上限；检查技术链是否存在不可达循环。
6. 建筑占地在地图范围内；禁止意外重叠及封死所有必要入口。
7. 联动优先级与平级次序明确；收益/代价文字和实际数值一致。

必需资源缺失时停止进入新局并说明具体资源。不能打印错误后继续暴露半初始化目录，也不能只用发布版可能移除的断言做业务验证。

### 19.2 一次卡牌事务

标准流程是 **定位实例 → 校验配置/阶段/前置 → 汇总费用并应用职业体力倍率 → 汇总资源变化 → 校验支付/等级 → 一次提交 → 消耗行动并按额度推进时段 → 发布结果 → 保存**。

- 同一种资源重复出现的费用必须相加；不能逐项通过而合计超支。
- 不能依靠每次扣费的 `clamp` 把负值抹成零，制造免费效果。
- 条件效果读取哪一个时点必须固定：本项目默认读取**操作开始前**的状态；同卡先建造再触发其额外收益，需要明确的分阶段语义与测试，不能偶然依赖效果排列。
- UI 预览必须使用与执行相同的条件、费用和派生入口。预览不得修改原局 RNG、历史、手牌、定义资源或磁盘文件。
- 多效果建造也必须校验实际变更的建筑和累计等级，不能只验证卡牌展示字段 `building`。
- 随机结果只在校验完成后、实际提交时生成；显示预览和鼠标悬停不能消费随机序列。
- 数值存储、运算、取整和容量上限必须明确。资源使用整数，伤害/位置使用浮点；取整时点集中在规则处，UI 只格式化。

### 19.3 规则发布与重入

提交完整状态后再发送通知。相邻信号的先后次序作为契约保持一致，监听者只能看到已提交状态。不得在刷新回调中重新调用同一次结算；延迟动画回调必须检查当前阶段/运行身份，不能让上一局回调影响新局。

持续效果到期、供电分配、人口变化、生产和缺粮损伤按第十节规定执行。跨夜恢复需要冻结的字段全部进入快照，不能用读档后的实时属性偷偷替换。

## 二十、性能、资源生命周期和异步

### 20.1 先记录，再优化

性能变更必须包含：Godot 版本、硬件、窗口尺寸、调试/导出模式、种子、天数、单位数、倍速、测量区间，以及修改前后的模拟时间/帧时间或分配指标。不能把 FPS 单次波动当结论。

优先找出耗时函数、调用频率和分配热点，再做局部改变并复测。官方建议使用 profiler 识别瓶颈；本项目不接受以“if 太多”“一定是 GDScript 慢”作为性能证据。[官方 CPU 优化](https://docs.godotengine.org/en/stable/tutorials/performance/cpu_optimization.html)、[4.5 优化原则](https://docs.godotengine.org/en/4.5/tutorials/performance/general_optimization.html)

### 20.2 热路径约束

- `_process`、模拟 `step()`、单位循环和 `_draw()` 中，不进行文件读写、ResourceLoader 加载或全场景查找。
- 不在每面围墙、每个单位的绘制中重复派生整座村庄属性；在状态变更时计算/失效缓存。
- 索敌频率、寻路频率、逻辑步长和绘制频率分别控制。路径重算必须保留当前移动段，避免慢速单位来回摆动。
- 目标可用直接类型化引用时，不让每颗弹体扫描全部敌人查 ID；验证目标存活并及时释放引用。
- UI 更新已有控件；手牌构成变化才增加或删除卡牌节点。库存变化不应重建与之无关的整棵界面。
- `_draw()` 不修改游戏状态；绘制所需稳定 Theme、StyleBox、字体和布局缓存复用。程序绘图可以保留，但大块静态画面应按变化失效，不追求每帧重绘所有静态内容。
- 当前 30 Hz 固定步长是基线；倍速只改变推进次数。每帧的积压步数要有明确上限/积压处理策略，避免慢帧引发持续追赶。
- 空间网格、对象池、MultiMesh、线程或 GDExtension 只在实际规模与测量支持时引入，并保持可验证的行为一致性。

### 20.3 所有权、线程与等待

- `RefCounted` 不能形成无意的强引用环；实体结束、弹体失效、退出一局时清理相关集合/连接。
- Node 的延迟释放与 Resource 的引用计数是不同生命周期，不能混用判断。
- `await`、Timer、Tween 或后台任务返回后，检查接收对象和当前局是否仍有效；切局/退出提供取消或忽略旧结果的机制。
- 未经 API 明确保证，不从工作线程修改场景树或共享 Resource。线程产出独立结果，在主线程提交；多线程是经验证后的选择，不是默认模板。
- Resource 缓存与复制语义按 4.5 文档核对；`resource_local_to_scene` 服务于场景实例，不自动解决纯模型的所有共享问题。[Resource API](https://docs.godotengine.org/en/4.5/classes/class_resource.html)

## 二十一、错误处理与存档补充要求

- UI 失败文案来自明确的操作结果；详细日志保留操作、相关 ID、资源路径和错误码，避免每帧刷屏。
- 自动保存失败必须可见，不能因为没有点击“保存”而静默丢失进度。失败后不得显示“已保存”。
- 校验完整的对象图：历史条目、战报、修正器操作类型、有限数值、快照数组和每个阶段必需数据都在恢复前检查。
- `REWARD` 阶段恢复后将进行黎明结算，也必须拥有有效的黄昏快照；不能只对 `NIGHT` 检查该字段。
- 存档版本只有一个权威定义。资源默认值、写入器、读取器和迁移测试必须一致。
- 单纯声明“临时文件 + 重命名”不代表跨平台替换一定成功；检查错误码，并验证目标平台上失败保留旧档的行为。
- 当前 `.tres` 存档仅面向本机可信文件。未来提供下载存档/模组时，要单独设计不执行脚本的导入边界，不能任意 `ResourceLoader.load()` 外部资源。
- 未做兼容迁移时明确拒绝旧版，并保留文件；不能静默创建空白局覆盖旧进度。

## 二十二、自动检查、评审门禁与验证矩阵

### 22.1 基础检查器

仓库提供无第三方依赖的检查器：

```sh
python3 tools/check_conventions.py
python3 tools/check_conventions.py scripts/main.gd scripts/resources
```

覆盖 `TYPE001` 显式变量/常量、`TYPE002` 循环类型、`TYPE003` 类型化容器、`TYPE004` 参数类型、`TYPE005` 返回类型和 `FORMAT001` LF 换行。它只做词法检查，屏蔽字符串和注释后检查明确规则；**不会证明 Godot 语法、资源引用、命名/文件顺序、事务或架构正确**。

运行失败必须查看具体项目。动态边界确有必要时依规范记录人工复核，不能全局关掉规则，也不能把已有问题加入静默忽略名单。当前仓库的失败项属于技术债，不等于检查器损坏。

### 22.2 验收顺序

| 门禁 | 通过条件 | 阻断情况 |
| --- | --- | --- |
| G0 范围与依赖 | 明确目标、状态所有权、失败行为、兼容影响 | 未读相关实现，准备盲目批量替换 |
| G1 静态规范 | 本次新增/修改代码符合强制规则；基础检查结果有记录 | 以 Variant/禁用警告规避类型问题 |
| G2 引擎解析与资源 | Godot 4.5 完成导入，无本次引入的脚本/资源错误 | 只查看退出码，日志仍报错 |
| G3 行为 | 相关正常/失败/边界测试通过，确实执行到目标分支 | 测试只加载脚本或复述实现 |
| G4 交互 | 涉及 UI 时实际运行、验证必要输入与状态 | 仅有 headless 结果却宣称 UI 已验收 |
| G5 交付 | 说明实际结果、日志和剩余债务；文档接口一致 | 沿用重构前成绩、遗漏未完成事项 |

完整项目发布前所有基础检查项和发布范围内行为门禁均需通过。单项维护不得恶化既有债务；遇到与当前改动直接相关的阻断，先修复再继续扩大功能。不能把“历史代码例外”用于新增同类问题。

### 22.3 必须覆盖的行为类别

- 资源：有效库、缺失/重复 ID、空嵌套资源、非法枚举/等级/数值。
- 卡牌：重复费用、正负效果、条件加成、不能支付、复用/消耗、预览隔离、多效果上限。
- 联动：加法/乘法顺序、资源争用、相同优先级、停电、污染、到期。
- 阶段：人口额度下三个时段、黎明更新、重复请求、失败结束、奖励只入手牌、第七夜与后续周期。
- 存档：往返、同路径覆盖后重读、快照深层隔离、版本不兼容、残缺阶段数据、失败不改原局/旧档。
- 战斗：固定种子、围墙破坏、不可达路径、目标死亡、同时死亡、Boss 和超时退出。
- UI：鼠标/键盘一致性、禁用、重复按键、弹窗期间暂停语义、读档后显示、不同窗口尺寸。

按本次改动选择相关类别，不要求每次改文案重跑全部战斗。修 bug 时增加能复现错误的行为检查，确认修复前失败、修复后通过；不为简单格式改动编写测试。

## 二十三、修改纪律、历史债务与 AI 交付

1. 先读本次涉及模块，写清楚变更范围和不变量；不在未验证迁移上叠加新系统。
2. 每轮修改完成一个可验证切片；改变数据接口时同步定义、资源、状态、UI 和测试。
3. 文本工具可用于机械编辑，但必须检查修改结果和调用方；禁止把大范围正则替换当重构验证。
4. 不删除用户已有修改、有效 `.uid` 或缓存外的资产；不手改 `.godot/` 来掩盖导入问题。
5. 新依赖说明用途、版本、许可和替代成本；开发检查不能无声依赖全局已安装工具。
6. 自动化命令不得覆盖玩家存档；网络、发布、提交消息等行动仍遵循用户授权。
7. 每个未解决问题记录位置、影响、验收条件和状态；`TODO` 必须引用记录，不能只写“以后优化”。
8. 基线变更、已知失败和完整验收状态放 [技术债清单](technical_debt.md)。关闭条目需要验证证据，不靠改成“已完成”。
9. 最终说明必须区分：修改了什么、实际运行了什么、结果是什么、哪些仍未验证。不得给出未测量的性能提升百分比。
10. 本规范的修订同时更新 `AGENTS.md` 和受影响的检查表/检查器；项目自主约束与引擎事实分开说明。

评审时使用 [代码评审与交付检查表](code_review_checklist.md)。目标是让新内容有明确位置、旧问题可定位、失败可复现，而不是让代码看上去“很架构化”。
